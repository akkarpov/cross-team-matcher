Запуск и эксплуатация
====================================================================================================

Локальный Windows-стенд
----------------------------------------------------------------------------------------------------

Требуются Python 3.11+, PostgreSQL 17 с postgres_fdw, pgcrypto и btree_gist.
Все адреса привязаны к loopback, данные и секреты находятся в ``.local``.
Существующие системные службы PostgreSQL не изменяются.

.. code-block:: powershell

   python -m venv .venv
   .\.venv\Scripts\python -m pip install -r requirements-dev.txt
   .\.venv\Scripts\python scripts/local.py init
   .\.venv\Scripts\python scripts/local.py db-start
   .\.venv\Scripts\python scripts/local.py setup
   .\.venv\Scripts\python scripts/local.py seed
   .\.venv\Scripts\python scripts/local.py start

Адреса: центр ``http://127.0.0.1:8100``, R1 ``http://127.0.0.1:8101``,
R2 ``http://127.0.0.1:8102``. Логины и случайные пароли учебных пользователей
записаны в ``.local/demo-credentials.json``. Это исключительно синтетические данные.
Системные роли и пользовательские пароли различны.

``status`` показывает состояние, ``stop`` останавливает процессы стенда.
Повторный ``setup`` не должен заменять пользовательские данные; обновление SQL
при разработке требует осознанной миграции, а не удаления каталогов.

Docker Compose
----------------------------------------------------------------------------------------------------

Выполните ``python scripts/local.py compose-env``: команда создаёт
согласованную конфигурацию и случайные секреты в ``.local/compose.env``.
Затем выполните инструкции из ``deploy/README.md``. Контейнеры имеют отдельные
тома; публикации и подписки создаются после согласованной установки схемы.
Compose поставляется отдельно от проверенного локального Windows-стенда.

Резервная копия
----------------------------------------------------------------------------------------------------

``python scripts/local.py backup`` готовит согласованный учебный комплект:
останавливает приложения, проверяет совпадение опубликованных наборов,
сохраняет очередь и квитанции вместе с данными каждого узла.
Закрытые сведения не входят в рабочую репликацию, поэтому нужен дамп
каждого владельца. ``restore`` восстанавливает в отдельные проверочные базы,
сравнивает контрольные состояния и не заменяет работающие основные узлы.
Точные параметры смотрите в ``python scripts/local.py --help``.

Физический standby — дополнительный сценарий; логический подписчик не
становится владельцем автоматически. Перед ручным promotion старый primary
должен быть исключён из записи. После потери WAL может потребоваться новая
синхронизация подписок. Эти действия описаны в ``deploy/failover``.
