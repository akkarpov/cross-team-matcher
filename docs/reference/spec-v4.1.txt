Содержание
Система подбирает сотрудников разных регионов, передаёт приглашения, фиксирует согласие, контролирует нагрузку и сохраняет историю участия. Приложение каждого региона использует одно подключение PostgreSQL и общие имена таблиц. Основные записи доступны через декларативные внешние секции; поиск и аналитика используют асинхронные копии.

1 Назначение и функции системы
Международная организация формирует проектные команды из сотрудников разных подразделений. Менеджер задаёт даты, позиции, обязательные компетенции и часы. Сотрудник получает приглашение и принимает либо отклоняет его. Часы занимают только подтверждённые назначения. Центральный офис ведёт каталог компетенций и анализирует результаты работы.
Роль
	Доступные функции
	Сотрудник
	Просмотр своего рабочего профиля, входящих приглашений, назначений и отзывов; ответ на приглашение.
	Региональный редактор
	Ведение профилей, компетенций, доступности и отсутствий сотрудников своего региона.
	Менеджер проекта
	Проекты и позиции; поиск с приоритетом своего региона; приглашения, завершение участия и отзывы о сотрудниках.
	Администратор каталога
	Создание и деактивация общих компетенций в центральной основной копии.
	Аналитик центра
	Отчёты по нагрузке, подтверждениям, участию и отзывам с указанием свежести данных.
	

Распределение требуется для независимой работы регионов при потере связи с центром и для общего поиска по межрегиональным копиям. Основные данные имеют территориального владельца; закрытые сведения остаются у него. Объём 300 сотрудников — только стенд, а не довод в пользу масштабирования.
Один код веб-приложения развёрнут в каждом регионе и в главном офисе. Роли определяют доступные формы. У каждого экземпляра один DSN к своему узлу; список адресов других БД и выбор соединения по сотруднику в приложении отсутствуют.
Для стенда используются вымышленные сотрудники. Межрегиональный обмен разрешён для ограниченного рабочего профиля. Закрытые идентификационные сведения и учётные записи остаются локальными. Никнейм не объявляется достаточным юридическим обезличиванием.

2 1 Контракт прозрачности
Архитектура является однородной федеративной распределённой БД: отдельные экземпляры PostgreSQL представляют общие отношения через локальные и внешние секции. Прозрачность расположения и фрагментации обеспечивается для схемы global. Это не единый физический PostgreSQL-кластер с автоматически общим каталогом и переключением реплик.
Интерфейс
	Гарантия
	global.employees и другие основные отношения
	Обычные SELECT, INSERT, UPDATE и DELETE. Значение owner_region выбирает секцию; её сервер указан в метаданных postgres_fdw.
	search.employee_profiles и связанные представления
	Чтение местных основных строк и местных реплик других регионов. Допускается отставание, указывается источник и время обновления.
	private.*
	Только локальные закрытые сведения и аутентификация. Намеренно исключены из глобального доступа.
	analytics.* на C
	Производные отчёты по консолидированным копиям, без запросов к работающим регионам при каждом открытии.
	

Приложение различает актуальные операции и предварительный поиск, но не выбирает физический сервер. owner_region — часть логического идентификатора, а не адрес подключения. Для некоторых общих SELECT PostgreSQL опросит несколько секций.
Одна внешняя секция имеет один источник для чтения и записи. Штатный PostgreSQL не переключает её автоматически на местную реплику при SELECT и обратно на владельца при UPDATE. Поэтому search и global имеют разные, явно описанные договорённости о свежести.

На R1 основная секция r1_data.employees локальна, а route.employees_r2 указывает на основную r2_data.employees сервера R2. Местная реплика r2_data.employees на R1 участвует только в search. 2 3 Секции и физические пространства имён
Каждый узел содержит схемы global, route, search и private. На владельце r1_data и r2_data содержат физические основные таблицы; на других узлах те же квалифицированные имена обозначают обычные таблицы-получатели репликации. К global прикрепляется только собственная основная таблица и внешние отображения чужих основных таблиц.
-- На R1, одинаковое логическое имя на каждом узле
CREATE TABLE global.employees (
 owner_region smallint NOT NULL,
 employee_id uuid NOT NULL,
 nickname text NOT NULL,
 active boolean NOT NULL,
 schedule_version bigint NOT NULL DEFAULT 0
) PARTITION BY LIST (owner_region);

-- Собственная основная таблица создаётся с PK и CHECK.
ALTER TABLE global.employees ATTACH PARTITION
 r1_data.employees FOR VALUES IN (1);

CREATE FOREIGN TABLE route.employees_r2
 PARTITION OF global.employees FOR VALUES IN (2)
 SERVER region2 OPTIONS
 (schema_name 'r2_data', table_name 'employees');
Пример показывает принцип размещения, а не полный установочный скрипт. SERVER и USER MAPPING создаются миграцией с ограниченными служебными правами; пароли в документ и репозиторий не включаются.
У родителя с внешними секциями не объявляются PK/UNIQUE-индексы. Физические основные таблицы имеют составной ключ (owner_region, id), фиксирующий регион CHECK и необходимые локальные FK. Внешнее отображение не создаёт глобальный контроль уникальности [3].

3 Репликация и консолидация

Рисунок 4 — Основные копии и асинхронные потоки репликации
C публикует cat.regions и cat.competencies в оба региона. R1 и R2 публикуют только собственные рабочие основные таблицы непосредственно друг другу и в C. Копии не включаются в публикации. Прямой обмен регионов не зависит от C. Изменять реплики пользователям запрещено [4, 5].

3 1 Настройка передачи изменений
На источниках используется wal_level=logical, выделенные роли и слоты. Для каждого источника создаются публикация его основных физических таблиц и подписки получателей. Начальная синхронизация должна завершиться для всех связанных таблиц до включения поиска. На получателе заранее создаются совместимые таблицы с теми же schema.table [5].
-- На R1: только принадлежащие ему физические строки
CREATE PUBLICATION r1_working FOR TABLE
 r1_data.employees, r1_data.employee_competencies,
 r1_data.capacity_periods, r1_data.assignments
 WITH (publish = 'insert, update, delete');
-- Остальные разрешённые рабочие таблицы добавляет миграция.
-- publish_via_partition_root остаётся false.

-- На R2: r1_data.* здесь обычные локальные реплики
CREATE SUBSCRIPTION from_r1
 CONNECTION 'host=region1 dbname=kfk user=replicator'
 PUBLICATION r1_working;
Одна подписка сохраняет порядок транзакций своего источника. Независимые источники не образуют единого синхронного снимка. Каталог центральных компетенций может временно отставать от рабочего потока региона; неопознанные ссылки в копиях не должны останавливать независимые подписки.
DDL, функции, права и последовательности не переносятся штатной логической репликацией как схема приложения [6]. Согласованные миграции выполняются отдельно. Используются UUID и неизменяемый owner_region. TRUNCATE и физическое удаление связанных бизнес-объектов через интерфейс запрещены.
Обычные бизнес-триггеры исполняются на основных таблицах, но не должны повторно запускать процесс на репликах. Пользовательские копии доступны только для чтения; очереди, секреты и закрытые данные в публикации не включаются.

3 2 Два варианта записи
Критерий
	Запись на любом узле
	Запись основной копии
	Окончательная запись
	В местную изменяемую копию
	В единственный основной фрагмент сотрудника
	Передача
	Рассылка уже совершённых изменений
	Сначала SQL к владельцу, затем репликация результата
	Две заявки на последние часы
	Возможны два независимых подтверждения
	Проверки сериализуются одной основной записью сотрудника
	Разделение сети
	Запись доступна, но возникают бизнес-конфликты
	Недоступный владелец не подтверждает новое назначение
	Механизм
	РБОК с разрешением конфликтов либо синхронным согласованием
	РОК и внешние секции; выбранная обязательная версия
	

В обоих вариантах пользователь может работать из своего региона. В выбранной версии он не выбирает удалённый хост: маршрутизацию обычного SQL выполняет PostgreSQL. Изменение считается подтверждённым только после успешной фиксации у владельца.
Асинхронные встречные подписки не обеспечивают безопасное master–master. Два узла могут записать разные строки назначений без конфликта первичного ключа, но превысить суммарную доступность. Разрешение по последнему времени не восстанавливает нарушенное обещание сотруднику [7].
Citus рассмотрен как альтернативный распределённый планировщик. Его синхронные reference tables не подменяют выбранную асинхронную модель. Применение Citus или другой СУБД в обязательную поставку этой редакции не входит.

6 Поиск и календарная модель
Форма поиска читает search.*: активные рабочие профили всех регионов, их компетенции и предварительную доступность. Все выбранные требования обязательны. Режим региона задаёт фильтр или первый ключ сортировки. Далее — доступное время и стаж по убыванию, составной идентификатор по возрастанию; страницы по 25 записей. Отсутствие данных не означает соответствие.
В учебной модели используются календарные даты и часы в неделю. Рабочие дни — понедельник–пятница, без национальных праздников. Недельный бюджет равномерно делится на пять рабочих дней. Полный день отсутствия имеет нулевой бюджет. Такой же способ распределения применяется к часам проекта. Время суток и часовые пояса в обязательной модели не учитываются.
Для каждого рабочего дня d в периоде назначения:
 capacity(d) = hours_per_week(d) / 5
 capacity(d) = 0, если d входит в отсутствие
 used(d) = сумма нагрузки назначений ACTIVE и CONFLICT
 допустить, только если used(d) + requested(d) <= capacity(d)
Ввод: даты начала и окончания включительно; начало не позже конца и есть хотя бы один рабочий день; положительные часы с шагом 0,5; недельный учебный предел 40 часов. Вычисления выполняются decimal/numeric без округления до целых часов. Неизвестная доступность исключает день из подтверждения.
Приглашение не резервирует часы. На момент принятия поиск выполняется повторно по основным данным владельца, включая навыки и стаж. Возможен отказ после положительной предварительной выдачи: местная реплика могла отстать. Дата источника и состояние синхронизации показываются в интерфейсе.

6 1 Приоритет региона при поиске
Менеджер должен иметь возможность выбрать режим поиска для каждой позиции проекта. По умолчанию используется «Сначала свой регион». Свой регион определяется полем owner_region проверенной учётной записи менеджера, а не IP-адресом, параметром URL или физическим расположением сервера приложения.
Режим
	Правило выдачи
	Сначала свой регион
	Все подходящие сотрудники своего региона выводятся перед подходящими сотрудниками остальных регионов.
	Только свой регион
	В результат включаются только подходящие сотрудники своего региона. Пустая выдача не расширяет поиск автоматически.
	Все регионы без приоритета
	Регион не влияет на порядок; действует общая сортировка по доступному времени, стажу и идентификатору.
	

Обязательные навыки, стаж, даты и доступность проверяются до регионального приоритета. Местный сотрудник, не соответствующий хотя бы одному требованию, не включается в выдачу. В режиме «Сначала свой регион» внутри местной и общей групп сохраняется одинаковая сортировка.
Порядок применяется ко всему результату до разбиения на страницы; счётчик учитывает выбранный режим. Режим сохраняется в project_positions.search_mode вместе с параметрами позиции и не сбрасывается при переходе между страницами или повторном входе. Допустимы OWN_FIRST, OWN_ONLY и ALL; неизвестное значение отклоняется сервером.
В форме явно показываются название своего региона и активный режим. Если местных кандидатов нет, режим «Сначала свой регион» показывает подходящих сотрудников других регионов; режим «Только свой регион» сообщает об отсутствии результатов и предлагает менеджеру самостоятельно сменить режим.
Поиск во всех режимах обращается к search.employee_profiles и связанным местным копиям через один DSN. Предпочтение региона не выбирает подключение к БД и не изменяет правила подтверждения у владельца сотрудника.

6 4 Атомарное подтверждение нагрузки
Снимок terms_snapshot хранит даты, часы, минимальный стаж и UUID всех требований. Он сохраняется в invitations и invitation_responses; согласие связано с версией и terms_hash, а не с изменяемой текущей позицией.
Приём команды начинается с фиксации её уникального идентификатора на адресате. Затем обработчик проверяет доверенный источник, права, состояние оферты и версию условий. Все затрагиваемые таблицы этого шага принадлежат одному узлу сотрудника; удалённых чтений и записей внутри обработчика нет.
-- Псевдокод владельца внутри одной транзакции
UPDATE r2_data.employees
SET schedule_version = schedule_version + 1
WHERE owner_region = 2 AND employee_id = :employee;

-- Затем прочитать актуальные capacity, absences, assignments.
-- Проверить принятые условия и каждый рабочий день.
-- INSERT assignment; UPDATE invitation_response;
-- INSERT workflow_event; INSERT outbox;
-- Записать результат processed_commands; COMMIT.
Одного SELECT FOR UPDATE недостаточно как универсального объяснения. postgres_fdw использует на удалённой стороне REPEATABLE READ, если локальная транзакция не SERIALIZABLE [2]. Реальное UPDATE строки schedule_version вынуждает конкурирующее изменение устаревшего снимка завершиться ошибкой сериализации. Вся операция повторяется в новой транзакции с прежним command_id.
Все изменения назначений, доступности и отсутствий соблюдают один guard: обновляют строку сотрудника до чтения суммарной нагрузки. Защита действует только при запрете обходного прямого DML. Отрицательная проверка не создаёт частичного назначения; бизнес-отказ сохраняется как результат и событие без списания часов.
Проверка двух параллельных удалённых подтверждений одного сотрудника обязательна: если оба вместе превышают бюджет, успешно завершается только допустимое назначение; повтор второй операции видит новую нагрузку.

6 5 Доставка и повтор операций
outbox записывается в транзакции вместе с исходным действием. Технический доставщик читает очередь и выполняет обычный INSERT в секционированное global.processed_commands через одно местное подключение. Адрес выбирает postgres_fdw по внешней секции. Доставщик управляет сроками повторов, а не физическим расположением данных.
Ситуация
	Правило
	Команда получена впервые
	На физическом листе адресата создаётся уникальная квитанция; обработчик меняет локальные данные и сохраняет результат той же транзакцией.
	Повтор того же command_id
	В новой транзакции читается готовый результат; source, kind и payload_hash должны совпадать.
	Повтор с другим содержимым
	Отклоняется как некорректное повторное использование идентификатора.
	Обрыв после удалённого COMMIT
	Результат неизвестен отправителю; повтор и чтение квитанции восстанавливают ответ.
	Доставка успешна, outbox ещё не отмечен
	Повтор безопасен. Отметка отправителя выполняется отдельной локальной транзакцией.
	

Гарантируется доставка с возможными повторами и идемпотентная обработка, а не физическая доставка «ровно один раз». INSERT ON CONFLICT DO UPDATE через FDW не используется. Конкурентный дубль обрабатывается уникальным ключом физической квитанции и последующим чтением результата после завершения конфликтующей транзакции.
При отправке запрещено одной транзакцией менять локальный outbox и бизнес-данные другого владельца. В PostgreSQL 17 postgres_fdw не поддерживает подготовку удалённых транзакций для 2PC [2]. Квитанции и исходящие сообщения сохраняются до завершения жизненного цикла проекта и установленного периода повторов.

6 6 Изменения и пограничные случаи
Случай
	Принятое правило
	Менеджер меняет условия после согласия
	Новая версия требует повторного согласия. Старое назначение действует до атомарной замены у владельца с пересчётом нагрузки без двойного учёта.
	Принятие и отмена одновременно
	Порядок определяет узел сотрудника. После принятия отменяется назначение; история согласия не удаляется.
	Отсутствие после назначения
	Отсутствие сохраняется; пересекающиеся назначения отмечаются CONFLICT и требуют пересогласования. CONFLICT не освобождает часы. Новые назначения на недоступные дни запрещены.
	Часть состава не подтверждена
	Принятые назначения занимают часы независимо. Проект FORMING; READY после заполнения обязательных позиций. Автоматического отката согласий нет.
	Отмена проекта
	CANCELLING до получения подтверждений отмены всех назначений, затем CANCELLED.
	Деактивация сотрудника
	Новые приглашения и принятия запрещены. Действующие обязательства явно отменяются или завершаются.
	Отзыв
	После завершённого участия; один отзыв автора на назначение; изменения журналируются.
	

Отмена, пришедшая раньше оферты, сохраняет терминальную отметку по invitation_id. Поздняя оферта не активируется; новое предложение получает новый ID. При отсутствии обязательной зависимости команда остаётся для повтора у доставщика, без окончательной квитанции об обработке.
READY описывает известные подтверждения состава, а не единый мгновенный снимок всех регионов. Проект и назначения имеют отдельные состояния; поздно пришедшее сообщение старой версии не возвращает объект из терминального состояния.
Превышение не допускается при новом подтверждении. Последующее отсутствие или уменьшение бюджета может сделать существующее назначение конфликтным; система не скрывает это и не считает такой состав полностью готовым.

6 7 Отзывы о сотрудниках
Система должна позволять менеджеру проекта оставить отзыв о сотруднике после подтверждённого завершения его участия. Отзыв связан с конкретным назначением (assignments), проектом и автором. Приглашение, отказ от приглашения или отменённое назначение не дают основания для отзыва.
Требование
	Правило
	Автор и права
	Менеджер с действующими правами на этот проект. Сотрудник и менеджер другого проекта не могут создать или изменить чужой отзыв.
	Содержание
	Оценка rating — целое число от 1 до 5; текст comment — от 1 до 2000 символов после удаления пробелов по краям. Проверка выполняется сервером.
	Уникальность
	Один отзыв данного автора на данное назначение. Повтор отправки не создаёт дополнительный отзыв.
	Редактирование
	Автор с сохранёнными правами может исправить оценку и текст. Версия и updated_at меняются; прежние и новые значения сохраняются в workflow_events.
	Просмотр
	Менеджер видит отзывы в карточке кандидата, сотрудник — отзывы о себе. Показываются проект, автор, оценка, текст, даты создания и изменения.
	

Регион проекта принимает отзыв по подтверждению завершения, полученному от владельца сотрудника через протокол команд. Пока подтверждение не доставлено, действие недоступно. Отставшая поисковая копия сама по себе не является разрешением на создание отзыва.
Основная запись reviews находится в регионе проекта. Создание или правка отзыва и событие истории фиксируются одной локальной транзакцией. Изменение с устаревшей version отклоняется. Рабочие отзывы и события асинхронно реплицируются в другие регионы и C; после своего сохранения приложение читает основную запись.
Ссылки на автора, сотрудника, проект и назначение после создания неизменны; физическое удаление через интерфейс не предусмотрено. При отсутствии записей показывается «Отзывов пока нет». Оценка не меняет обязательные фильтры и базовую сортировку кандидатов. Новых таблиц для этой функции не требуется.

7 1 Права и границы данных
Закрытая карточка, логины, хеши паролей и контакты находятся в private своего региона. Они не объявляются внешними секциями, не входят в публикации и не включаются в глобальные дампы. Никнейм и UUID обозначают рабочий профиль, но не гарантируют необратимого обезличивания [11].
Приложения входят в доверенную серверную часть: устанавливают личность по локальной сессии, запрещают клиенту подменять actor_id и передают только проверенные действия. FDW-соединения используют отдельные роли источников. Получатель выводит source_region из доверенного подключения и сопоставляет его с командой; значение из браузера не является доказательством права.
Сотрудник отвечает за себя через свой домашний регион. Межрегиональные служебные команды ограничены типами доставки оферты, отмены и подтверждения результата; сервисная роль другого региона не может подделать согласие сотрудника. Права менеджера на проект проверяются у владельца проекта до отправки оферты.
Прямое редактирование копий и обход обработчиков календаря запрещены GRANT. Доступ приложений к global ограничивается разрешёнными столбцами и бизнес-операциями. Физические таблицы, SERVER, USER MAPPING и репликационные роли недоступны обычным пользователям.
SQL параметризуется; TLS применяется к внешним соединениям; порты БД закрыты от браузеров. Журнал не содержит паролей, токенов и закрытых профилей. Отзывы и события проверяются на запрещённые персональные сведения. На стенде используются синтетические записи.

8 Отказы и разделение сети
Отказ
	Поведение
	C недоступен
	Местные операции и прямые R1↔R2 работают при доступной связи; новые справочники и центральная аналитика недоступны.
	R2 недоступен
	search на R1 может читать последнюю копию R2 с отметкой устаревания. Подтверждать новые назначения сотрудников R2 нельзя.
	Разрыв R1↔R2
	Каждый регион обслуживает своих владельцев. Команды другого региона остаются в очереди; полная актуальная выборка global может завершиться ошибкой.
	Одна подписка отстала
	Копия временно неактуальна. Основные записи продолжают работать, если живы их владельцы.
	Приложение R1 выключено
	Интерфейс R1 недоступен; другие экземпляры и БД продолжают работать.
	Сбой после записи на владельце
	Повтор command_id и чтение результата; неизвестный ответ не трактуется как отсутствие записи.
	Конфликт применения репликации
	Подписка останавливается; исправляется причина и проверяется согласованность, транзакция не пропускается молча.
	

Прозрачность расположения не означает прозрачность отказа. PostgreSQL не заменяет недоступный основной фрагмент его репликой автоматически. Один полный запрос global, затрагивающий недоступного владельца, не возвращается как полный успешный результат.
Для управляющих запросов задаются согласованные тайм-ауты соединений и statement_timeout. Учебная цель — сообщить о недоступности до 10 секунд; это критерий испытания, а не измеренный результат. Ожидающая команда не подтверждает занятость.

8 2 Резервирование и восстановление
Репликация рабочих профилей в другой регион не является полной резервной копией регионального узла: закрытые сведения, учётные записи и очереди там отсутствуют. Для восстановления сохраняются резервные копии каждого источника и миграции общей схемы, внешних отображений и подписок.
Дополнительно можно развернуть физический standby каждого регионального PostgreSQL в той же стране. Он резервирует весь экземпляр, включая private и служебные таблицы. Это отдельный сценарий высокой доступности; межрегиональные логические подписчики автоматически не повышаются до владельцев.
Этап
	Действие
	Подготовка копии
	Для согласованного учебного комплекта временно запретить запись, дождаться доставки очередей и подписок, сохранить копии и контрольные числа.
	Восстановление владельцев
	Поднять основные узлы и проверить ключи, версии, назначения, события, outbox и квитанции.
	Восстановление копий
	Восстановить совместимые схемы; слоты и подписки восстановить по проверенному сценарию либо пересоздать копии из источников.
	Возобновление работы
	Проверить повтор команд, нагрузку, готовность таблиц подписок и доступность внешних секций.
	

При ручном переключении на standby прежний primary должен быть гарантированно отключён от записи. Иначе появляются два владельца. Сохранность ещё не доставленного WAL, состояние слотов и возможная повторная синхронизация проверяются отдельно. Автоматический failover не заявляется.
Слоты репликации контролируются по удерживаемому WAL и месту на диске. После утраты необходимого WAL требуется повторная синхронизация получателя. Плановая цель восстановления из подготовленных копий — 30 минут на зафиксированном стенде.

9 Стенд и демонстрация прозрачности
Базовый стенд: C, R1 и R2 как отдельные PostgreSQL 17 с независимыми адресами и томами; три экземпляра одного приложения. Используются postgres_fdw и штатная логическая репликация. btree_gist может применяться для локальных ограничений пересекающихся периодов. dblink, Citus и отдельный прокси не входят в основную конфигурацию.
-- Один и тот же запрос на R1 и R2
SELECT owner_region, employee_id, nickname
FROM global.employees
WHERE owner_region = 2 AND active;

-- План должен показывать нужную внешнюю секцию на R1
EXPLAIN (VERBOSE, COSTS OFF)
SELECT employee_id, nickname
FROM global.employees WHERE owner_region = 2;

-- Поиск по местным основным строкам и репликам
SELECT owner_region, employee_id, nickname
FROM search.employee_profiles WHERE active;
На защите показываются метаданные секционирования, SERVER и обезличенное USER MAPPING, Remote SQL в EXPLAIN, место фактической записи и последующая доставка её копий. В коде приложения не должно быть списка соединений регионов или обращения к физическим таблицам r1_data/r2_data.
Плановый набор: 300 сотрудников, 150 компетенций, до 20 компетенций на человека и 5 одновременных пользователей. Ориентир ресурсов полного стенда — 4 vCPU, 8 ГБ RAM и 20 ГБ SSD; достаточность проверяется измерением. Конкретные версии образов фиксируются при сборке.

9 1 Функциональные приёмочные проверки
Тест
	Критерий
	Т01 Права
	Чужой actor_id, регион и проект в запросе не дают права редактирования или согласия.
	Т02 Полнота требований
	Отсутствие одного обязательного навыка исключает кандидата; неизвестные сведения не считаются подтверждением.
	Т03 Календарь
	Проверяются границы дат, неполная неделя, день отсутствия и несколько пересекающихся назначений.
	Т04 Приглашение
	До принятия нет списания часов; отказ оставляет доступность прежней.
	Т05 Параллельное принятие
	Два удалённых подтверждения на последние часы не создают превышения; ошибка сериализации корректно повторяется.
	Т06 Принятие и отмена
	Итог единственный, история обоих действий сохранена, позиция не переоткрыта до подтверждения.
	Т07 Изменение условий
	Увеличение часов требует новой версии и повторного согласия; замена не считает старое назначение дважды.
	Т08 Отзывы и история
	До подтверждённого завершения отзыв запрещён; чужой менеджер и дубль отклоняются. Оценка 1–5, текст 1–2000; правки сохраняют историю и версию.
	Т17 Режим поиска
	Проверить все три режима, приоритет до пагинации, пустой свой регион, сохранение выбора и исключение неподходящих местных кандидатов.
	

Каждая проверка имеет заранее определённые входные данные и ожидаемые записи. История должна объяснять изменение состояний; наличие непустой выдачи или таблиц недостаточно. Функциональные тесты выполняются через тот же SQL-контракт, который использует приложение.

9 2 Распределённые испытания
Тест
	Критерий
	Т09 Маршрутизация
	Обычный SQL к global на R1 изменяет основную запись R2; приложение не выбирает хост. EXPLAIN подтверждает внешнюю секцию.
	Т10 Асинхронные копии
	Изменение профиля и правка отзыва с событием появляются в копиях других регионов и C. Копия защищена от записи.
	Т11 Центр выключен
	Местный вход, профиль и местное назначение работают; прямой обмен регионов продолжается.
	Т12 Владелец недоступен
	Поиск показывает устаревшую копию; новое назначение не подтверждается. Очередь восстанавливается после связи.
	Т13 Потерянный ответ
	Повтор command_id не создаёт дубль назначения, события или списания часов.
	Т14 Схема и подписки
	Начальная загрузка, порядок миграций и перезапуск не запускают повторно бизнес-триггеры на копиях.
	Т15 Резервная копия
	Восстановлены рабочие и закрытые данные, очередь и квитанции; контрольные состояния совпадают.
	Т16 Производительность
	После 10 прогревочных поисков не менее 100 измерений; цель p95 ≤ 3 с на зафиксированном наборе.
	

В протоколе фиксируются версии, ресурсы, задержки сети, состояние слотов, фактическое отставание копий, входные SQL и результаты. Цель доставки при исправной связи — до 10 секунд на стенде; жёсткая верхняя граница при отказах не обещается.
Эта редакция содержит проект и план проверки. Запуск кластера, готовность миграций, результаты нагрузочных и отказных тестов не утверждаются без отдельного протокола.

10 Соответствие требованиям проекта
Требование
	Решение
	Единая логическая БД
	Одинаковые global-отношения и SQL на узлах; декларативная маршрутизация локальных и внешних секций.
	Отсутствие самописного прокси

	Оферта, ответ, назначение и отмена через команды, локальные транзакции и подтверждения.
	История и аналитика
	События сохраняются с изменением; центр получает консолидированные рабочие копии.
