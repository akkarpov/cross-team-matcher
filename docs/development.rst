Команда, этапы и версии
================================================================================

Участники и границы работ
--------------------------------------------------------------------------------

Распределение взято из :download:`исходного HTML-плана <reference/original-plan.html>`.
Это зоны ответственности команды. Авторство отдельных коммитов определяется
самим Git; имена участников не подставляются в историю автоматически.

Исходный план предусматривал работу 6–14 октября 2026. Сохранённый протокол
реализации датирован 7 октября. Плановые даты не выдаются за даты коммитов
или фактическое время выполнения. ``assessment.md`` отдельно описывает
четыре технических направления реализации; они не заменяют три роли из плана.

Этапы реализации
--------------------------------------------------------------------------------

#. Контракт ТЗ 4.1: владельцы, один DSN, операции и ошибки.
#. Три узла: локальный стенд, роли, FDW и логическая репликация.
#. Данные: 19 отношений, закрытые поля, календарь, search и analytics.
#. Приложение: аутентификация, пять ролей, адаптивные рабочие экраны.
#. Согласованность: outbox, атомарная квитанция, schedule_version и повтор команд.
#. Интеграция: исправления приватности, состояний, слотов и интерфейса.
#. Поставка 4.1.0: испытания, протокол, документация и лабораторная.

Это ретроспектива по артефактам, а не перечень семи ранее опубликованных
релизов. Подробные ссылки на файлы и сопоставление исходных десяти задач
хранятся в ``report/content.json`` и отображаются на главной странице отчёта.

Порядок дальнейшей разработки
--------------------------------------------------------------------------------

Использовать ветки из первоначального плана: ``karpov/stand``, ``lebedev/sql``
и ``krechun/ui``; для отдельной задачи добавлять понятный суффикс.
Каждый участник коммитит из собственного аккаунта со своей настроенной
Git-идентичностью. Ветки создаются участниками при начале реальных работ.

#. Создать ветку от актуального ``main`` и описать ожидаемый результат задачи.
#. Изменения контрактов согласовать до изменения зависимых SQL и форм.
#. В PR указать поведение, затронутые файлы, проверки и ограничения.
#. Проверить соответствующий слой: SQL, HTTP, браузер или распределённый стенд.
#. После ревью объединить PR; обновить журнал изменений и отчёт при новом этапе.

Стабильная версия задаётся в ``pyproject.toml``, ``app/__init__.py`` и
``docs/conf.py``. ``report/content.json`` должен содержать тот же номер;
сборщик проверяет его против ``pyproject.toml``. Изменения версий описываются
в ``CHANGELOG.md``. Теги ставятся на реально проверенные коммиты.

Сборка отчёта и GitHub Pages
--------------------------------------------------------------------------------

Отчёт статический, сервер приложения и PostgreSQL ему не нужны.
Исходники: ``report/index.html``, ``report/report.css``, ``report/report.js``
и ``report/content.json``. Метрики берутся из существующего
``docs/evidence/acceptance-summary.json``. История — из ``git log`` текущего
checkout; ссылки на код закрепляются за SHA сборки.

::

   python -m pip install -r requirements-dev.txt
   python scripts/build_pages.py
   python -m playwright install chromium
   python scripts/check_pages.py
   python -m http.server 8120 --directory dist/pages --bind 127.0.0.1

Открыть http://127.0.0.1:8120. Готовые файлы находятся в ``dist/pages``:
отчёт в корне, справка Sphinx в ``docs/``. ``build.json`` содержит версию,
SHA, время сборки UTC и последние 30 коммитов. Для локальной копии без
``.git`` доступен ``--git-dir PATH`` к отдельному checkout; этот режим нужен
только для просмотра фактической истории при подготовке публикации.

Workflow ``.github/workflows/pages.yml`` проверяет сборку в PR и публикует
после push в ``main``. Он собирает Sphinx с ``-W``, выполняет модульные
проверки и браузерную проверку отчёта. В Settings → Pages источником
публикации должен быть выбран GitHub Actions. Сайт:
https://akkarpov.github.io/cross-team-matcher/ .

В публичную сборку входят только отчёт, выбранные скриншоты и документация.
Рабочие базы, сессии и файлы ``.local`` не копируются. Этот сайт объясняет
проект; для работы самого приложения нужен отдельно запущенный стенд.

Кнопка «Печать / PDF» открывает стандартную печать браузера. Перед печатью
раскрываются таблица задач и списки файлов, фильтр этапов не скрывает историю.
