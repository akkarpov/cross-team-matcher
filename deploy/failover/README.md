# Ручное восстановление владельца и необязательный standby

Базовый стенд имеет по одному владельцу C/R1/R2 и логические рабочие копии.
Они не содержат всех private-данных и не становятся владельцами автоматически.
Ни данный runbook, ни межрегиональные подписки не заявляют автоматический HA.

## Восстановление из проверенного архива

1. Остановить приложения и workers соответствующего узла. Зафиксировать отказ
   старого primary и исключить его повторное подключение к записи. Проверить
   время/контрольную сумму архива `.local/backups/.../manifest.json`.
2. Проверить архив командой `python scripts/local.py restore --backup ...`.
   Команда создаёт три отдельных read-only БД `matcher_restore_*`, сравнивает
   все строки и сохраняет `restore-*.json`. Она **не** заменяет основные БД.
3. Для настоящей аварии подготовить новый PostgreSQL 17 того же региона,
   применить роли и согласованные миграции. Восстановить нужный архив в чистую
   БД без подписок с `pg_restore --single-transaction --no-subscriptions`.
   Секреты/USER MAPPING берутся из защищённой конфигурации владельца.
4. Проверить private.accounts, employee_private, outbox, processed_commands,
   назначения, schedule_version, события и контрольные суммы. Нельзя считать
   рабочую копию другого региона достаточным источником private-данных.
5. До открытия записи согласовать источники репликации. Если сохранились
   согласованные replication slots и WAL, проверить их позиции. Если нет —
   создать чистые получатели рабочих копий из восстановленных источников и
   новые подписки с начальной синхронизацией. Не включать `copy_data=true`
   поверх уже заполненных таблиц: это создаёт конфликты первичных ключей.
6. Обновить FDW SERVER только после проверки единственности владельца. Дождаться
   `pg_subscription_rel.srsubstate='r'` для всех таблиц; проверить маршрутизацию,
   outbox retry, идемпотентные квитанции и ограничения нагрузки. После этого
   возобновить приложения. Остальные регионы всё это время показывают свежесть
   своих локальных поисковых копий.

## Необязательный физический standby

Это отдельное расширение стенда, которое фактически не разворачивалось при
базовом протоколе. Оно потребует дополнительного экземпляра PostgreSQL и
отдельного тома в стране соответствующего владельца.

Подготовка администратора:

- Разрешить replication только для адреса standby и выделенной роли в
  `pg_hba.conf`, использовать SCRAM/TLS и защищённый password file.
- Снять физическую базовую копию утилитой PostgreSQL 17:
  `pg_basebackup -h PRIMARY -p PORT -U PHYSICAL_REPL -D NEW_EMPTY_DATA -R -X stream -C -S STANDBY_SLOT`.
  Каталог обязан быть новым и пустым; слот — уникальным и контролируемым по WAL.
- Настроить отдельный порт и `hot_standby=on`, запустить standby и проверить
  `pg_is_in_recovery()`, `pg_stat_wal_receiver` и отставание LSN. Сохранять
  standby и приватные данные в регионе владельца.

Ручное переключение:

1. Гарантированно отключить старый primary от записи (процесс, сеть, endpoint).
   Если это нельзя доказать, **не выполнять promotion**: возможны два владельца.
2. Зафиксировать replay LSN, проверенное отставание и потенциальную потерю
   последних подтверждённых изменений. Асинхронный standby не даёт RPO=0.
3. Выполнить `pg_ctl -D STANDBY_DATA promote`, дождаться завершения recovery.
4. Проверить владельца, private-данные, очереди, квитанции и локальные ключи.
   Проверить пригодность логических slots/WAL; при необходимости пересоздать
   подписчиков. Автоматическая сохранность logical slots здесь не настроена.
5. Обновить FDW endpoint и единственный локальный DSN приложения, повторить
   проверки T09/T10/T13/T14 и только после этого открыть запись.

Старый primary нельзя просто вернуть в сеть. Его заново синхронизируют с новым
владельцем по отдельному плану (`pg_rewind` при выполнении его предусловий или
новая base backup). Прямое превращение логического подписчика в primary в этой
системе запрещено архитектурой.
